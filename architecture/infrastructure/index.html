Infraestrutura¶

Ambientes¶

O projeto tem dois ambientes:

Ambiente Banco SSL Uso
Local (dev) PostgreSQL via Docker desabilitado Desenvolvimento e testes
Produção (prod) Neon PostgreSQL obrigatório Dados reais do observatório

O ambiente local é descartável. Você sobe, testa, derruba. Os dados reais ficam no Neon.

Veja Configuração para detalhes das variáveis de ambiente de cada ambiente.

Docker (Ambiente Local)¶

Docker Compose com dois serviços para desenvolvimento:

PostgreSQL¶

Container principal com o banco de dados.

# docker-compose.yml
services:
  postgres:
    image: postgres:latest
    container_name: ofrj_postgres
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql
      - ./docker/init.sql:/docker-entrypoint-initdb.d/init.sql

O init.sql é executado automaticamente na primeira inicialização e:

  1. Cria os schemas raw, staging, marts
  2. Concede permissões ao usuário ofrj
  3. Configura o search_path padrão
  4. Habilita as extensões uuid-ossp e unaccent

pgAdmin (opcional)¶

Interface web para gerenciamento do banco. Só sobe com o profile tools:

./scripts/pgadmin.sh
# ou
docker compose --profile tools up -d

Acesso em http://localhost:5050 com as credenciais do .env.

Neon (Produção)¶

O banco de produção é um Neon PostgreSQL serverless. Mesmo PostgreSQL, mas gerenciado na nuvem.

Na prática, a diferença para o código é mínima: muda o host, a senha e liga SSL. O pipeline (ingestão Python + dbt) funciona igual nos dois ambientes.

Para rodar o pipeline contra produção, basta configurar as variáveis no .env:

DB_HOST=ep-xxx-xxx-123456.us-east-2.aws.neon.tech
DB_PASSWORD=sua_senha_neon
DB_SSLMODE=require
DBT_TARGET=prod

Cuidado com produção

O pipeline faz DROP + CREATE nas tabelas raw. Rodar ingestão contra produção apaga os dados existentes e recarrega do zero. Isso é intencional (carga full), mas tenha certeza de que é isso que você quer antes de apontar para o Neon.

Rede Docker¶

Todos os containers compartilham a rede ofrj_network.

Volumes¶

Volume Conteúdo
postgres_data Dados persistentes do PostgreSQL
pgadmin_data Configurações do pgAdmin

Cuidado

./scripts/clean.sh apaga os volumes com docker compose down -v, destruindo todos os dados do banco.

dbt¶

Configuração do Projeto¶

Definida em dbt_project/dbt_project.yml:

  • Profile: observatorio_feminicidio
  • Variável global: rj_state_code: 33 (código IBGE do RJ)
  • Materialização por camada:
    • staging/* → views
    • marts/core/* → tabelas
    • marts/violence/* → tabelas
    • marts/aggregate/* → tabelas

Profiles¶

Definidos em dbt_project/profiles.yml:

Target Threads SSL Uso
dev 4 desabilitado Desenvolvimento local
prod 8 obrigatório Produção (Neon)

Schemas gerados pelo dbt¶

O projeto usa uma macro generate_schema_name customizada que faz o dbt usar os nomes de schema diretamente, sem prefixo:

Schema no dbt_project.yml Schema criado no banco
staging staging
marts marts

Isso garante consistência entre dev e prod. A macro fica em dbt_project/macros/generate_schema_name.sql.

Acesso Externo (Power BI)¶

O banco de produção tem um usuário somente leitura (powerbi_reader) para conexão de ferramentas de BI. Esse usuário tem SELECT em todos os schemas e não pode modificar dados.

Para conectar no Power BI, use o schema marts que contém o modelo dimensional completo.

Veja os guias Neon (Produção) e Power BI para detalhes de conexão e gerenciamento de usuários.

Python¶

Gerenciador de Pacotes¶

O projeto usa uv para gerenciamento de dependências Python:

uv sync          # Instala todas as dependências
uv run <cmd>     # Executa dentro do ambiente virtual

Dependências Principais¶

Pacote Uso
asyncpg Conexão assíncrona com PostgreSQL (protocolo COPY)
pandas Leitura e manipulação de DataFrames
sqlalchemy Abstração de banco (não usado diretamente na ingestão)
python-dotenv Carregamento do .env
tqdm Barras de progresso na ingestão
unidecode Transliteração de caracteres acentuados
openpyxl Leitura de arquivos .xlsx
xlrd Leitura de arquivos .xls
odfpy Leitura de arquivos .ods
